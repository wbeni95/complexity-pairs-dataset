# generators/

Scripts that **systematically manufacture** candidate pairs: an input specification goes in, and
complete entries come out (entry.json, implementations, harness, README). Every generated entry
then goes through the same validator as hand-written ones. We keep these scripts even when their output
has low value on its own. They are reusable infrastructure, and the starting point for real search.

## Two classes, and the rule that separates them

| Class | Example | What its output is |
|---|---|---|
| **Mechanical transformation** | un-memoising a recurrence; rewriting a cheap algorithm wastefully | **T7 synthetic** (START_HERE section 5): low signal, stored in `synthetic/`, never counted as a validated pair |
| **Search with an exact verifier** | tensor-decomposition search (`search/`), superoptimisation | a candidate pair only if it **beats the best known algorithm** and passes verification; a rediscovery of a known result is a pipeline check |

Mechanical generators are useful for testing the pipeline and as training data for "un-bloating". They
are not evidence about hard problems, because a model trained only on them learns to undo the obvious
(START_HERE section 5).

## Rules for new generators

- Derive the cost claims from the specification (e.g. λ from the characteristic polynomial), not by fitting.
  The V2 fit is the check, not the source of the claim.
- Generated code carries a "generated by" header. Regenerate instead of editing.
- Tag honestly (T7 for mechanical output), test the generator under `tests/test_generators*.py`, and log
  what it produced in RESEARCH_LOG.md.
